## Sync drift: 2026-10-19

- Stale: FR-1 names the hierarchy "mission → milestone → feature" but the code has a fourth level, the slice. `packages/core/src/missions/mission-types.ts:936-939` documents the hierarchy as "Mission → Milestones → Slices → Features", `mission-types.ts:975-985` types `MissionWithHierarchy.milestones` as `Array<MilestoneWithSlices & { slices: SliceWithFeatures[] }>`, and `packages/core/src/postgres/schema/project.ts:1734-1756` defines the `slices` table with `mission_features.sliceId` as its foreign key (`project.ts:1758-1761`). `packages/core/src/missions/mission-types.ts:948-973` (`selectNextSerialMissionSlice`) admits only one pending slice at a time, so a slice is a scheduling unit, not a display detail.
- Stale: FR-3 claims the system manages "goals, objectives, and key results", but no objective or key-result field, type, or table exists. The goal model is `{ id, title, description, status }` only (`packages/core/src/goals/goal-types.ts:5-12`), the `goals` table has exactly `id`, `title`, `description`, `status`, `createdAt`, `updatedAt` (`packages/core/src/postgres/schema/project.ts:1664-1675`), and a search of `packages/core/src/goals` and `packages/engine/src/goals` for `objective`, `keyResult`, and `key_result` returns nothing. `docs/goals-refinement-gate.md:9,16` states the opposite of FR-3: "Success metrics live in slice/feature text for v1 rather than a structured `successMetric` schema" and "Fusion must not build a structured `successMetric` schema ... because they seem plausible in advance."
- Stale: FR-5 says the system scores "task/feature outcomes", but evals score tasks only. `packages/core/src/postgres/schema/project.ts:1472-1500` (`eval_task_results`) carries `taskId` and a `taskSnapshot`, and has no feature column or foreign key. `packages/core/src/eval/eval-types.ts:318-321` types `EvalTaskResult` the same way. Feature-level scoring is the mission validation loop (`mission_validator_runs`), which is a different surface.
