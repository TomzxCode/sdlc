## Sync drift: 2026-10-19

### Missing requirements

- **The session advisor (live LLM transcript review) layer has no FR or NFR.** The shipped code adds a second, model-driven oversight tier: `packages/engine/src/overseer/overseer-advisor-service.ts`, `packages/engine/src/overseer/overseer-advisor-runtime.ts`, `packages/engine/src/overseer/overseer-advise-tool.ts`, `packages/engine/src/overseer/overseer-session-delta.ts` and `packages/engine/src/overseer/overseer-watchdog.ts`. It is gated by the `plannerOverseerAdvisorEnabled`, `plannerOverseerAdvisorProvider` and `plannerOverseerAdvisorModelId` workflow settings declared in `packages/core/src/workflows/builtin-workflow-settings.ts:729-754` and resolved in `packages/engine/src/project-engine.ts:4037`, `:4119` and `:4139`. Its delivery policy lives in `packages/core/src/planner/overseer-emission-guard.ts` (suppress content-free notes, one note per update, never repeat a note at equal or lower severity).

- **Plan locking and spec drift reporting have no FR or NFR.** `packages/core/src/planner/spec-lock.ts` canonicalizes the approved plan into `Mission`, `File Scope`, `Steps`, `Acceptance Criteria`, `Non-goals`, `Dependencies` and `Lineage` sections and exposes `isSpecLockActive`. `packages/core/src/planner/drift-report.ts` evaluates scope creep, silent expansion and plan deviation and returns an alignment of `on-plan`, `diverged-needs-review`, `diverged-relocked-approved` or `unavailable`. The evidence is durable in the `spec_locks`, `current_plan_evidence` and `spec_drift_reports` tables (`packages/core/src/postgres/schema/project.ts:408-418`), written by `appendCurrentPlanEvidence` and `appendSpecLock` (`packages/core/src/store.ts:1459` and `:1516`), read back through `GET /api/tasks/:id/spec-lock` (`packages/dashboard/src/routes/register-task-workflow-routes.ts:5005`) and rendered in Task Detail as "Spec lock alignment" (`packages/dashboard/app/components/TaskDetailModal.tsx:4939-4982`). No requirement states that an approved plan is locked, that later plan edits invalidate the approval, or that scope creep is reported.

- **The human-control guard also withholds on approval-blocked tasks, which FR-6 and the Constraints section do not mention.** `OverseerHumanControlWithholdReason` is `"user-paused" | "approval-blocked" | "auto-merge-off-human-review"` (`packages/engine/src/overseer/overseer-human-control-policy.ts:59`) and the approval branch is checked first, at `:93-95` via `isTaskBlockedOnApproval`. FR-6 names only the user-paused and auto-merge-off cases.

- **The operator runtime oversight controls have no requirement.** Nudge, Stop and Explain are exposed as `POST /tasks/:id/overseer/nudge`, `POST /tasks/:id/overseer/stop` and `GET /tasks/:id/overseer/explain` (`packages/dashboard/src/routes/register-task-workflow-routes.ts:5138`, `:5155` and `:5172`), implemented by `nudgeOverseerTask` (`packages/engine/src/project-engine.ts:2258`), `stopOverseerTask` (`:2317`) and `explainOverseerTask` (`:2363`). Stop writes the per-task `plannerOversightLevel: "off"` override and the per-task `sessionAdvisorEnabled: false` override (`:2330-2333`). The per-task level override is also settable from Task Detail (`packages/dashboard/app/components/TaskDetailModal.tsx:5446`, `data-testid="detail-oversight-level-select"`). No FR requires the operator to be able to steer, stop, or inspect the overseer, and no FR requires that Stop writes the per-task `off` override.

- **The overseer layer owns a veto that blocks a task from reaching done through an empty merge, and no FR covers it.** `packages/engine/src/overseer/overseer-noop-finalize-veto.ts` implements `deriveExecutorSignalMemory` and `evaluateNoOpFinalizeExecutorVeto`, and `packages/engine/src/merge/merger-ai.ts:2099` records the `overseer:no-op-finalize-vetoed-failed-executor` run-audit event when the veto fires. This is a lifecycle decision taken from overseer state, not an intervention record, so FR-5 does not describe it either.

### Stale requirements

- **FR-4 no longer matches the code, because the live path never reaches a human confirmation.** `decidePlannerRecovery` returns `action: "none"` for the `merger` and `pull-request` stages whenever `autoMergeWillProceed === true` (`packages/core/src/planner/planner-recovery.ts:240-253`). `PlannerRecoveryController.tick` computes `autoMergeWillProceed = allowsAutoMergeProcessing(task, ...)` (`packages/engine/src/overseer/planner-recovery-controller.ts:300`) but withholds the whole task first when `allowsAutoMergeProcessing` is false (`:251-265`), so the only reachable tick state has `autoMergeWillProceed === true` and the `await_confirmation` branch is never taken. `resolveConfirmation` has no production call site (the other references are the definition, doc comments and the test file), the PR-advance handler is a deliberate no-op (`packages/engine/src/project-engine.ts:2700-2709`), and no destructive or external handler is wired at all (`packages/engine/src/project-engine.ts:2711-2715`). The classification itself is also level-independent: `packages/core/src/planner/planner-confirmation.ts:1-19` states that merge/PR and destructive actions are confirmation-required "regardless of the effective oversight level", so no level selects it. The dedicated suite states the unreachability directly and is skipped: `packages/engine/src/__tests__/planner-recovery-controller-confirmation.test.ts:39-43`.

- **NFR-3 names the wrong surface for the oversight level.** The level is not a Settings control. It is a workflow setting edited in the Workflow Editor Values tab (`packages/dashboard/app/components/workflow-setting-display.ts:169-181` groups `plannerOversightLevel` under the workflow `oversight` group; the write path is `packages/dashboard/app/api/system/workflows.ts:148`). `docs/settings-reference.md:454` states that the project or global default is set through the Workflow Editor Values tab and not in Project Settings. The Settings modal carries only the session-advisor default (`packages/dashboard/app/components/settings/sections/GeneralSection.tsx:746-771`), and the per-task override lives in the New Task dialog and Task Detail. NFR-3 should say "Workflow Editor Values tab plus Task Detail".
